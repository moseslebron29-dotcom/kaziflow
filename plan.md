# KaziFlow implementation plan

## Product scope and implementation approach

Build the requested Kenyan/African microtask and digital-advertising platform as a real full-stack application, not a static landing page. Preserve the requested member, administrator and advertiser workflows: password-based registration/login/profile recovery; activation-gated tasks and the one-time KES 100 fee; configurable task categories; WhatsApp Status Ads with user-submitted evidence and human review; wallet ledger, M-Pesa withdrawal requests, referrals, administrator management, campaign funding and advertiser reporting; policy/support pages; and installation, deployment, environment and API documentation.

The initialized project is React + TypeScript + Wouter on the client, Express + tRPC on the server, and Drizzle over the platform-managed MySQL-compatible database. The user prefers PostgreSQL, but the native Manus WebDev database is MySQL; use this supported persistent service unless the user later chooses and supplies an external PostgreSQL service, which would require a deliberate dialect/DSN migration. Development and published versions share this project database, so do not add fabricated account, campaign, task, payment or earnings seed data. Empty states must reflect real records. Test logic without issuing fake customer payments or touching live wallet records.

Use explicitly requested email/password authentication rather than substituting Manus OAuth. Hash passwords server-side; enforce server-side validation, roles, secure session cookies, login/reset rate limits, single-use email/reset tokens and authorization at every financial or administrator operation. Keep application cookies separate from platform-reserved names. Send cookies as `HttpOnly`, `SameSite=None; Secure` for HTTPS Preview and the published origin; allow plain-HTTP local development only through an explicit local configuration, not a `NODE_ENV` or internal-request-scheme heuristic. Email verification and password reset use Brevo's server-side transactional API when a verified sender and API key are configured; never expose reset tokens or Brevo keys to unauthenticated browser state or logs.

Use MySQL transactions and a durable, append-only wallet ledger as the accounting source of truth. Keep activation payment attempts, Daraja callbacks/queries, task and advertising submissions, review decisions, withdrawals and payout references as separate auditable records. Enforce idempotency and unique provider references in the database. Reserve withdrawal balances transactionally. Only successful, server-verified activation payments unlock member tasks; only approved submissions create ledger credits; only completed, evidenced payments can transition a withdrawal to Paid. Advertiser campaigns remain inactive until confirmed funding is recorded. Never seed fake success or payout evidence.

For task completion, distinguish what the application can verify from what it cannot. Use server-tracked task attempts and specified evidence/review rules; do not describe a client event as independent proof of a social-media action or a human video view. WhatsApp Status Ads submissions will require the campaign reference, posting date, status image and insights image, pass duplicate-file checks and enter an administrator queue. Admins configure rate per view, minimum and maximum eligible views, budget, duration and participating-member limits. Reward calculation is server-side and capped; human approval precedes credit. Tell members and advertisers plainly that user screenshots are evidence submitted by the member, not independent verification of each viewer, and let campaigns demand stricter evidence.

M-Pesa activation will use a server-only Safaricom Daraja integration. The activation record stays pending until an authenticated server callback is processed idempotently and the transaction status is confirmed with Daraja; a browser response must never activate an account. Daraja values have now been supplied to the managed project environment, but no live or sandbox payment has been triggered. The server fail-closes production STK requests unless a separate go-live flag is enabled. A public HTTPS callback and provider-side end-to-end verification still need confirmation. Brevo email verification and password-reset delivery require a Brevo API key, a verified sender and the production HTTPS site origin. Never simulate a successful payment or email to make a flow appear complete. Withdrawals retain reserved funds; Paid remains unavailable until an actual M-Pesa B2C or equivalent disbursement and its confirmation are integrated.

## Design direction

- **Design Movement:** Contemporary editorial fintech with the restraint of a well-run regional cooperative ledger, expressed as an original web product rather than an imitation of the reference.
- **Core Principles:** Honest evidence over hype; calm visual hierarchy; mobile-first task discovery; transaction states that are easy to understand.
- **Color Philosophy:** Warm paper and mineral neutrals make the application readable; deep ink anchors financial information; a distinctive vermilion accent marks action and progress. Avoid the reference's green-led visual identity and do not use gradients as a substitute for hierarchy.
- **Layout Paradigm:** Editorial landing page with asymmetric text/ledger modules; compact app shell with a narrow desktop sidebar and mobile bottom navigation; task details and financial summaries get distinct, purpose-built compositions rather than repetitive cards.
- **Signature Elements:** A small interlocking “K”/path wordmark; ledger-style ruled separators and aligned KES amounts; a restrained vermilion status chip for the next required action.
- **Interaction Philosophy:** Clear confirmation before money-affecting actions, named statuses and next steps, no fake live indicators, helpful empty states, keyboard-accessible forms and predictable mobile navigation.
- **Animation:** Short opacity/position transitions for route changes and menus only; respect reduced-motion preferences; avoid pulsing balances or animated claims.
- **Typography System:** Manrope for headings and Inter for interface/body text, with tabular numerals for money and quantities; use a clear, compact scale that preserves readable touch-sized controls on mobile.
- **Brand Essence:** A clear route from verified digital work to accountable records for members and advertisers; practical, candid, dependable.
- **Brand Voice:** Direct and locally legible without promising a level of income. Example: “Choose a task. Check its requirements. See what happens next.” “Your wallet changes only after an approval or a confirmed payment.”
- **Wordmark & Logo:** Custom KaziFlow lettering with a simple path/ledger mark; no borrowed LipaTask symbol or default-font-only logo.
- **Signature Brand Color:** Vermilion (`#C6533B`), used selectively for the primary action and noteworthy states.

## Application structure

- `client/src/pages/`: separate public, account, member, WhatsApp campaign, advertiser, administrator, wallet and policy/support routes.
- `client/src/components/`: responsive app shell, mobile navigation, form fields, status labels, confirmation dialogs, transaction tables and reusable campaign/task content.
- `client/src/lib/`: tRPC client, typed form validation helpers and currency/date display helpers.
- `server/_core/`: Express bootstrap, session/cookie handling, rate limiting and request context; keep callback HTTP handlers outside ordinary client-controlled state changes.
- `server/`: domain services and routers for auth, users, tasks, submissions, WhatsApp campaigns, wallet/ledger, Daraja payments, withdrawals, referrals, advertiser funding, administration, policy and support. Keep calculation and payment-validation logic in testable server modules, not React components.
- `drizzle/schema.ts` and additive `drizzle/` migrations: user/account state; auth tokens and sessions; task definitions/attempts/submissions; advertisers and campaign records/funding/submissions/evidence; payment attempts and callback references; wallet accounts/ledger; withdrawal holds/requests/payout references; referral rules/events; settings, announcements and audit events.
- `public/manus-routes.json`: static manifest for every user-facing route, kept in sync with `client/src/App.tsx`.
- Root documentation: `.env.example` with names and placeholders only, installation and deployment instructions, API contract and payment/callback setup notes; no actual secret values.

## Delivery boundaries

The implementation covers the requested product areas with the platform-managed persistent database and server-side authorization. Successful application state is stored in MySQL and survives process restarts/redeployments, but no automated point-in-time database backup has been configured; the owner must rely on available point-in-time website exports or arrange a separately approved backup target. Brevo email delivery requires the protected key, verified sender and a valid public HTTPS origin. Daraja payment initiation remains fail-closed for production until separately approved. Advertising review remains manual unless a campaign supplies stronger verifiable evidence; screenshots are not independent viewer proof. Draft policy copy is transparent and is not a legal compliance certification. No publish or GitHub push occurs without a separate owner request.
